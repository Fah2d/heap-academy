## What and why

The parts of WP-4.3 that the interface will call, each built test first:

1. **The validation checklist** (`src/grader/validation.ts`; FR-ADM-07, FR-GRD-05). The five rules of `04-content-system.md` section 4.1, in the order of `03-experience.md` section 7.6. Each failed rule says what to fix: the missing parts, the test cases the solution did not pass, the wrong answers that pass everything, and the programs that reached the time limit. If the owner stops a validation, no rule is decided.
2. **Test case list changes** (`src/grader/test-case-list.ts`; FR-ADM-05): add, duplicate, move up, move down and delete, with the limit of 12. `testCaseProblems` names every field that is empty or too long, with its limit, so the editor can give each field its own message.
3. **The hash of the gradable content** (`gradableText` in the grader, `gradableHash` in `src/features/admin/gradable-hash.ts`). The browser and the server compute the same SHA-256 (Web Crypto). The text has a fixed shape, so equal content gives an equal hash whatever the key order, and no text can move between fields without changing the hash.
4. **The save action** (`saveLesson`) now carries the lesson's test cases, parsed by the grader's one parser. It also takes an optional `validatedHash`. It sends `p_validated = true` to `save_lesson` only when that hash equals the hash of exactly what it saves (section 4.2). Its answer reports `validated`. Before this change, the save re-sent whatever test cases were already stored.
5. **`setLessonStatus`**: publish, unpublish and archive the version the editor loaded. It follows the states of section 4.3. A lesson that was not validated since its last gradable change answers `needs_validation` (the database's `lesson_not_validated`). A newer version answers `stale`. The published-content cache expires on success.
6. **The validation runner** (`src/features/admin/client/validate-lesson.ts`, `controller-checks.ts`; FR-ADM-06). It checks the solution, then the starter, then each wrong answer, using the learners' runtime controller, each program on a fresh worker. It gives the checklist, the hash of what it checked, and the solution's result per test case (for the verdicts and "Fill from solution"). It stops at the first stopped check, or when the runtime fails.
7. The lesson editor's loader reads the stored test cases through the grader's parser, and the editor sends them with every save.
8. **The test case list** (part 2; `src/features/admin/components/test-case-list.tsx`; FR-ADM-05, `03-experience.md` section 7.5). A "Test cases" section in the lesson editor and its side list. Each test case is a disclosure titled "Test case 2: <name>" that opens to name, input, expected output, how to compare, hint and follow-up code, with the field descriptions of section 7.5. Add, Duplicate, Move up, Move down and Delete use the grader's list functions, so the limit of 12 is the grader's: at 12, Add and Duplicate are gone and a sentence says why. Focus stays in the list after every change (the new test case's name; the pressed move button, or the other at an end; the next test case or Add after a delete). New IDs are `crypto.randomUUID()`, passed in so tests fix them.
9. **Saving with test cases** (part 2). Save checks every test case with `testCaseProblems` before sending. A problem opens its test case in the same render, focus goes to the first invalid field in page order, and each field shows its own message with its limit ("Keep the expected output to 5,000 characters."). Test case edits count as unsaved changes. The published-lesson note and the `needs_validation` message now name test cases too.
10. The `Disclosure` primitive takes `isExpanded` and `onExpandedChange` (React Aria's own controlled props), so the editor can open a test case with a problem. Uncontrolled use is unchanged.
11. Two new states in `/dev/admin`: a lesson with 12 test cases, and a lesson with a test case that has no name and an expected output over the limit. The empty lesson now also shows "No test case yet".

12. **Validate in the lesson editor** (part 3; `src/features/admin/components/validation-panel.tsx`; FR-ADM-06, FR-ADM-07, section 7.6). A fifth section, "Publish", in the side list. It shows Python's state, the five rules in order with "Passed", "Failed" or "Not checked" (icon and word), and for a failed rule what to fix: the missing parts, the test cases the solution did not pass by number and name, the wrong answers that pass everything, the programs that reached the 5 second limit. Validate runs the checklist; while it runs it is pending ("Validating") and Stop appears. A live region says "Validating the lesson", "Stopping the validation", "Validation finished. Every rule passed.", "Validation finished. 2 rules failed." or "Validation stopped. No rule was decided." A note says when the lesson changed after the last validation.
13. **Python in the editor** (`src/features/admin/client/validation-runtime.ts`). The learners' runtime controller starts when the editor opens and ends when it closes ("Python loading" in section 8). A failed start says so, with Try again; Validate then says at once that nothing was checked, instead of waiting for a Python that will not come. A restart between two programs (the fresh worker per program) does not show as loading.
14. **Stop** (`controller-checks.ts` `cancel`, `validate-lesson.ts` `isStopped`). Stop ends the check that has begun through the controller, whose stopped results end the validation; a check still waiting for Python is dropped and never begins. The runner reads the stop after every check, so a stop is never reported as an unavailable Python, and nothing runs after it.
15. **The verdict per test case and "Fill from solution"** (`src/features/admin/validation-view.ts`, `test-case-list.tsx`; section 7.5). After a validation that ran the solution, each test case shows "What the solution printed": the verdict with its reason (and Python's message with its line for an error), and the output, or "Nothing was printed", and a note when it was cut at 64,000 characters. A result is shown only while it still describes the test case: the same solution, input and follow-up code. Once the expected output or the comparison changes, the output stays and the verdict gives way to "Validate again for a verdict". "Fill from solution", under the expected output, copies the output when the solution ran to its end (passed, or printed something else), the output was not cut, and it differs from the expected output; focus then goes to the expected output field.
16. **The validated hash on Save** (T-22). Save sends `validatedHash` only when the last validation passed and the gradable content it saves is exactly what was checked (wrong answer labels trimmed as the save trims them). The server still compares it with its own hash of what it saves.
17. **A validation that throws** (a defect, such as results that do not match the test cases) leaves "Validating" for "Python could not run the programs" and still reaches the page's unhandled rejection reporting.
18. **Gallery** (`/dev/admin`, `gallery-runtimes.ts`): the editors get a Python the gallery controls, so the page starts no worker. The verdicts come from the grader's `grade` on output fixed per test case. New states: Python loading (Validate waits until Stop), Python failed, validating (a check that never ends), and a lesson whose second test case expects the greeting without the prompt, so the solution fails it and "Fill from solution" is offered.

19. **The lesson's status** (part 4; `src/features/admin/components/lesson-status.tsx`; FR-ADM-09, section 7.6). Under the checklist, a "Status" group says what the lesson is and who can see it, and offers the moves of section 4.3. Publish appears only when the last validation passed for the lesson as it is now in the editor, title, address and instructions included (`checkedNow(...).whole`); until then a sentence says when it will appear. Move back to draft from a published lesson, and Archive, ask first in a dialog that says what learners will see. Move back to draft from an archived lesson asks nothing. After a move, focus goes to the sentence that names the new status, and a live region says it. A refusal shows its reason in the group, with Reload for a newer version.
20. **Publish saves first.** Publish puts the lesson on the site as it is in the editor: it checks the form (a wrong field is marked and focused, and nothing is sent), saves with the validated hash, then calls `setLessonStatus` with the version the save returned. A refused save stops there and shows the save's reason in the Publish section.
21. **Save on a published lesson validates first** (section 7.6). Unless a passing validation already covers the lesson as it is, Save runs Validate, shows "Validating" and Stop, and saves with the hash only after a pass. A failed rule, a stop, or a Python that could not run saves nothing, and the message says which and where to look. Save stays pending while that validation runs. The validation runs outside React's transition, because updates inside an async transition are held until it ends, which hid "Validating" and Stop (found by a test).
22. `runValidation` returns the validation's result, so Save can use it. Validate's own path still sends a defect to the page's unhandled rejection reporting; Save's path reports it with `reportError` and saves nothing.
23. Gallery: every lesson editor gets a status action; the draft's succeeds (so Publish can be pressed after Validate), the refusing one answers `status_not_allowed`, and a new state shows an archived lesson.

24. **J-13** (part 5; `e2e/j13-publish-journey.spec.ts`; FR-GRD-05, FR-ADM-06, FR-ADM-07, FR-ADM-09). Against the local stack, an admin at aal2 creates a course, a chapter and a lesson, writes its instructions and one test case, and validates three times in the learners' Python: a solution that fails the test case (rule "The solution passes every test case" fails and names the test case; no Publish), a starter that already passes (rule "The starter fails at least one test case" fails with its reason; no Publish), then a lesson that passes every rule. Publish then saves and publishes; the status survives a reload; Move back to draft asks with what learners will see, and moves it. Axe on the refused, published and dialog states.
25. **The runbook** `docs/runbooks/published-lesson-wrong.md` (07-operations section 8.1): take the lesson off the site with Move back to draft (or Archive), check as a guest that it is gone, fix and validate, check the solution's output by eye, publish again; a SQL Editor path in the production dashboard for when the dashboard cannot be used; what to record after. Every control and message it names was checked against `src/messages/admin.ts` and the components; the public addresses (`/learn/<course>/<lesson>`, `/courses/<course>`, `/courses`) are those of `03-experience.md` section 3, built in WP-5.1 and WP-5.2.
26. **A flaky test fixed** (`lesson-editor.test.tsx`, "asks before archiving, then moves an archived lesson back to draft without asking"). It failed once in a full `pnpm verify` run and passed 5 of 5 alone. Cause: the new status renders before the move's async transition ends (updates after an `await` in a transition are not held), and React Aria's pending Button sets `aria-disabled` and ignores presses, so under load the second click fell in that window. The test now waits for the button to stop being pending before pressing it. The component is unchanged: a person sees the pending button for that moment.

## Open decisions

1. **Unpublishing the last published lesson of a published course.** The database refuses to *publish* a course with no published lesson. It does not stop the course's last lesson from being unpublished or archived, which leaves a published course with nothing in it. The spec does not say. Options: (a) allow it, and the course page shows its empty state; (b) refuse it in the lesson trigger with a reason, the way the course publish guard refuses. Recommendation: (b), as a new migration with a trigger test, in a follow-up once you answer. Default if no answer: (a), as built.
2. **The wrong answers' labels are part of the hash.** The database already treats a label change as a gradable change (the whole `wrong_answers` column), so the hash includes the labels too. Recommendation: accept. Default: as built.
3. **Where the checklist lives.** `src/domain` may not import `src/grader` (architecture section 4.1), and the rules read the grader's test results, so the checklist is in `src/grader`. Recommendation: accept. Default: as built.

4. **Test case fields are plain text areas.** Input, expected output and follow-up code use the monospace text area, not the CodeMirror editor. Section 7.5 does not ask for the editor, and twelve test cases with three editors each would load 36 editors on one page. Recommendation: accept. Default: as built.
5. **Delete asks nothing.** Deleting a test case takes effect in the editor at once, like removing a wrong answer; nothing is stored until Save, and leaving with unsaved changes asks first. Recommendation: accept. Default: as built.

6. **One action for the verdicts.** Section 7.5 asks for "one action" that runs the solution against every test case and shows each verdict. Validate is that action: it runs the solution first, and its results give the verdicts and "Fill from solution". There is no separate "Run the solution" button. Recommendation: accept. Default: as built.
7. **Python starts when the editor opens.** It loads the Pyodide files (several megabytes, cached after the first time) on every visit to a lesson editor, so Validate is quick. The alternative is to start it at the first Validate. Recommendation: accept. Default: as built.
8. **When a verdict stops showing.** A test case's output is shown while the solution, the input and the follow-up code are unchanged; its verdict also needs the same expected output and comparison. Recommendation: accept. Default: as built.

9. **Save on a published lesson always validates, even for a title-only change.** Section 7.6 says Save on a published lesson validates, then saves. Section 4.4 says a change to the title, instructions, hints or XP "saves at once". As built, Save follows 7.6 literally: a title fix on a published lesson needs Python to load and the checklist to pass. The alternative is to validate only when the gradable content differs from what was saved. Recommendation: keep it as built for this release, because it never saves a published lesson that fails the checklist. Default: as built.
10. **Publish saves the editor's content first.** Publish publishes the lesson as it is in the editor, so it saves any unsaved change with the validated hash before the status move. The group says so ("Publish saves the lesson as it is in the editor, then puts it on the site."). The alternative is to offer Publish only when nothing is unsaved. Recommendation: accept. Default: as built.
11. **Move back to draft and Archive keep unsaved changes unsaved.** They change only the status. The edits stay in the editor, still marked unsaved. Recommendation: accept. Default: as built.

As built, Publish is not offered at all until every rule passes, and the checklist gives the reason on the failed rule. There is no Publish press that is then refused, except the database's `needs_validation` answer, which the unit tests cover. Recommendation: accept. Default: as built.
